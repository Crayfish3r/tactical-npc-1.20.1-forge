# Repository rules for Codex / AI agents

Goal: independent, challenging, server-authoritative PvP NPCs on Minecraft 1.20.1 / Forge 47.4.20 / Java 17 / TaCZ 1.1.8-hotfix2. NPCs 2.1.0 is an optional compatibility adapter and a separately identified comparison target. Preserve its equipment/rendering/spawn systems when changing that adapter; the independent entity must not require its classes or resources.

## Authority and sources
- This file owns general project rules; `.agents/skills/*/SKILL.md` owns specialized procedures. Reports are dated evidence, not proof that the current code implements or passes a requirement. Distinguish published commits, local drafts, executed checks and human acceptance.
- Read numerical tuning from [ServerConfig](forge-addon/src/main/java/dev/zuma/tacticalnpc/config/ServerConfig.java), including effective profile methods and world overrides. Weapon metadata and [WeaponProfile](ai-core/src/main/java/dev/zuma/tacticalnpc/core/WeaponProfile.java) own weapon tuning. Algorithmic validity/safety caps remain in their checking core/adapter classes. Link to those owners instead of copying numeric limits into skills; never describe a code constant as a configurable setting.
- Confirm exact APIs for the layer being changed against pinned sources/binaries and [INTEGRATION-AUDIT](docs/INTEGRATION-AUDIT.md). Missing NPCs artifacts block NPCs-specific signatures, adapter compilation or optional runtime checks, not pure-core or independent-navigation work. Aggregate Gradle tasks may compile the optional adapter: distinguish that build prerequisite from an independent runtime dependency.

## Runtime constraints
1. Preserve `perception -> immutable snapshot -> decision -> action arbitration -> Forge/TaCZ adapter`. The Java core must not import Minecraft, Forge, TaCZ or NPCs classes.
2. Only the server thread mutates entities, inventories, movement, memories or world state. Workers may process immutable snapshots only. Validate generation, identity, dimension, order/target validity and TTL before applying results or deferred commands.
3. A single controller owns movement and weapon requests. Prevent duplicate goals/firing and competing base AI; release ownership and per-level state on cancellation, death, removal, unload and dimension change. Fail safely on unsupported adapters.
4. Native TaCZ owns shot creation, cooldown, reload, bolt, modes and ammo. Do not hand-spawn production bullets, fabricate reserves outside the implemented ammo policy, or restart native operations every tick. Revalidate physical obstacles and ally safety for each actual native round.
5. Use bounded, fair per-owner/per-level queries, rays, candidate checks and path searches, with cache invalidation and backoff. No full-world scan each tick, unbounded search, synchronous tick I/O or chunk tickets/forced loads from production target/route search. Activation cannot make an unticked entity tick.
6. Keep planning cadence distinct from execution cadence: reuse a selected route while applying necessary movement/safety inputs each active server tick. Physical completion and action-specific admissibility govern special transitions; ordinary standing checks must not silently substitute for them.
7. Prefer events, extension interfaces or verified source changes over Mixins. Any necessary Mixin needs exact signatures, a version gate, fail-soft behavior and dedicated-server verification. Add an AI library only for a demonstrated need.
8. Preserve third-party licenses and attribution. Permission to reuse source is separate from modpack redistribution.

## Information and difficulty
- Hard uses legitimate visual, last-seen, hearing, damage or received squad observations. Never refresh hidden position/velocity through a live entity reference; DIRECT fire requires current visual LOS. Keep reaction, turn, accuracy and observed-velocity limits distinct.
- Explicitly enabled Unfair has only the implemented exceptions: stronger effective hearing; faster effective perception/reaction/reacquisition and squad delivery; periodic quantized hidden-player hints; and the independent entity's infinite-reserve override with ordinary native reload. Hard restores that entity's saved ammo policy, which need not itself be finite. Do not assume the reserve override exists in the optional NPCs adapter.
- Hints remain `UNFAIR_HINT`, nonvisual, with zero hidden velocity and their own expiry/storage; they never become VISION or visual squad reports. Hard clears them. They may authorize checked known-area search/suppression, never DIRECT tracking, obstacle penetration, native cooldown bypass or allied damage. Preserve existing neutral/eligibility restrictions.
- Verify these contracts in [UnfairHints](forge-addon/src/main/java/dev/zuma/tacticalnpc/combat/UnfairHints.java), [TacticalCombatGoal](forge-addon/src/main/java/dev/zuma/tacticalnpc/combat/TacticalCombatGoal.java), [TacticalNpcEntity](forge-addon/src/main/java/dev/zuma/tacticalnpc/entity/TacticalNpcEntity.java) and the core observation/squad contracts before changing them.

## Workflow and evidence
- Read the relevant project skills, current sources/configuration and recent reports before editing. Work in small testable slices; keep instruction-only changes separate from implementation.
- Before running checks, identify changed files, affected behavior and the minimum sufficient set in a few lines; use [TESTING-PROFILES](docs/TESTING-PROFILES.md), not a separate large plan. For each additional run, state what changed since the previous run and why that scope is needed.
- After a local fix, run the specific test or smallest affected set. Investigate FAIL before retrying; after fixing it, repeat the failing test and necessary related regressions. Resume interrupted matrices from unfinished scenarios only when saved results remain applicable. Keep original failures; never retry an unstable test until a random PASS.
- Complete one final STAGE assessment after functional changes. Reuse successful checks already covering the final relevant inputs instead of launching a duplicate STAGE; disclose coverage assembled across runs. Applicability includes production code, tests, shared fixtures/helpers, resources, configuration, dependencies and runtime. A change invalidates affected coverage, not all history; uncertainty warrants a small expanded set with a reason. Do not rerun an unchanged successful set merely for confidence.
- FULL is required only on explicit owner request, before release, or for a concrete cross-cutting risk that selective checks cannot sufficiently cover. Multiple changed files alone do not justify it. Combined checks cover optional-adapter, shared-integration or mixed-runtime risks; do not repeat the entire standalone set in combined after each local fix. An available adapter alone does not mandate combined for every task.
- Run relevant core suites when ai-core or its contracts change; scoped compile/GameTests for affected Forge behavior; ordinary dedicated save/restart for persistence, migration, lifecycle, configuration-loading or packaging changes. JFR, load matrices and soak require their corresponding risk or an explicit request. Instruction/documentation-only edits need static links/frontmatter/diff checks and no game JVMs.
- Before release, use the applicable FULL and requested combat/load/performance coverage; identify human 1v1/1v4 and production-JAR checks separately. Dated reports and completed-stage requirements are historical evidence, not continuing run mandates; the current policy and current owner instructions govern validation.
- Preserve before/after baselines and failed receipts. Report exact versions, scope, commands, actual counts/results, artifact identity and unresolved risks. NO-SOURCE, dry-run, partial/zero execution and reading a report are not a PASS. Lower firing volume or fewer active NPCs is not a performance win.
