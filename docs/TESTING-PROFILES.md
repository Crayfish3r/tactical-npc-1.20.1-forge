# Профили проверок Tactical NPC

## Действующая политика — 2026-10-22

Общие правила: [AGENTS.md](../AGENTS.md); измерительные процедуры: [forge-ai-profiling](../.agents/skills/forge-ai-profiling/SKILL.md). Эта политика по явному разрешению владельца заменяет прежнее требование завершать патч команд FULL standalone и combined. Исторические отчёты и требования завершённых этапов не задают обязательные прогоны новой задачи. Прежняя редакция с аудитом и итогами пакета 07–14 сохранена в [архиве](TESTING-AUDIT-2026-10-19.md); её результаты и FAIL остаются датированными свидетельствами.

Перед запуском в нескольких строках укажи изменённые файлы, затронутое поведение и минимально достаточные проверки. Отдельный большой отчёт не нужен. Для каждого дополнительного прогона объясни, что изменилось после предыдущего и почему нужен именно этот набор. Если новый запуск не нужен, укажи применимые сохранённые результаты и основание их использования.

| Проверка | Когда и какой объём |
|---|---|
| Статическая | Только документация/инструкции: ссылки, frontmatter skills и diff. Игровые JVM не нужны. |
| FAST / локальный набор | Конкретный тест или минимальный затронутый набор после локальной правки. После FAIL сначала исследовать причину, затем проверить исправление и необходимые связанные регрессии. |
| STAGE | Одна итоговая оценка покрытия новых и затронутых регрессий после завершения функциональных изменений. Уже прошедшие проверки на окончательных соответствующих входах засчитываются без обязательного повторного запуска STAGE. Если покрытие собрано несколькими запусками, сообщить это явно. |
| FULL | По явному запросу владельца, перед релизом либо при конкретном сквозном риске, который нельзя достаточно проверить выборочно. Несколько изменённых файлов сами по себе не основание. FULL запускает весь актуальный каталог выбранной среды без фильтра. |
| Combined (`--legacy`) | При риске для optional adapter, общей интеграции или взаимодействия runtime; также при явном запросе этой среды. После локальной правки выбирать затронутые adapter/mixed-runtime сценарии, без повторения всего standalone-набора. Наличие optional dependencies само по себе не обязывает запускать combined. |
| Core | Релевантные suites при изменении ai-core или его контрактов; расширение до всех suites обосновать затронутыми контрактами. Состав suites берётся из текущего `ai-core/run-tests.sh`, количества — из фактического вывода. |
| Ordinary dedicated save/restart | При изменениях сохранения, миграций, lifecycle, загрузки конфигурации или упаковки. Проверить соответствующее поведение обычного сервера, включая сохранение и повторную загрузку. |
| JFR / нагрузочная матрица / soak | При соответствующем риске производительности, бюджетов, длительного удержания состояния либо по отдельному запросу. Human 1v1/1v4 и production-JAR playtest учитывать отдельно. |

Выбирай среду FULL по заявленному риску, релизному объёму или запросу; combined определяется строкой выше. Сам FULL не добавляет автоматически JFR, soak и все исторические матрицы. Требования релиза и отдельного эксперимента фиксируются явно. Недоступные optional зависимости блокируют затронутую optional проверку, а не самостоятельные independent/core результаты.

## Применимость результатов и повторные прогоны

Оценивай входы проверки, а не только имя теста: production-код и контракты, сам тест, общие fixtures/helpers и порядок/изоляцию сценариев, ресурсы/арены, конфигурацию, зависимости и runtime. Для измерений также важны host/JVM, seed/map, оружие, warmup, окно измерения и фактически active/ticking actors. Одинаковое имя в standalone и combined не делает результаты взаимозаменяемыми.

Новая правка инвалидирует результаты в затронутой области, а не всю историю. Например, изменение общего fixture затрагивает все использующие его сценарии; комментарий в инструкции не инвалидирует Java GameTests. При неясной зависимости выбери небольшой расширенный набор и объясни причину. Не запускай неизменённый успешный набор «для уверенности».

После FAIL изучи лог и причину до повторения. После исправления повтори проблемный тест и необходимые связанные регрессии. Не повторяй нестабильный тест до случайного PASS; диагностируй нестабильность, сохрани исходный FAIL и сообщи, что осталось неизвестным. Успех после исправления дополняет историю, а не переписывает её.

Прерванную матрицу продолжай с незавершённых сценариев, если для завершённой части есть достоверные результаты и её входы остаются применимыми. Учти зависимости от общих fixtures, порядка и состояния runtime; если их нельзя подтвердить, повтори только эту затронутую часть с объяснением. Оборванный общий лог без доказательства завершения конкретных сценариев не даёт им PASS. Не ослабляй проверки полноты ради возобновления.

Итоговый STAGE — сверка требуемого покрытия с применимыми результатами на окончательных входах. Он может состоять из нескольких запусков FAST/STAGE и связанных проверок; укажи selection, среду, receipts и оставшиеся пробелы. Это не новый единый прогон. Выборочный успешный повтор после неудачного FULL нельзя называть новым полностью зелёным FULL; исходный FULL остаётся FAIL либо INTERRUPTED. Частичные результаты нескольких запусков не подменяют receipt целого FULL.

## Команды и защита достоверности

Команды выполняются из корня репозитория, кроме явно отмеченных Gradle-команд. `python` означает рабочий Python 3, `bash` — Git Bash на Windows. `--offline` допустим только с готовым pinned cache. Перед запуском сверяй selection с текущими исходниками и каталогом launcher; примеры ниже не определяют достаточность будущей задачи.

```powershell
bash ai-core/run-tests.sh territory patrol
python tools/testing/run-gametests.py FAST --tests ModeCommandTests#permissionSuggestionsAndOldCommandSurface --offline
python tools/testing/run-gametests.py STAGE --tests ModeCommandTests,TeamCommandTests,NpcNameTests --offline
python tools/testing/run-gametests.py STAGE --legacy --tests WeaponScenarioTests#nativeModesAndBurst --offline
```

Только при выбранном по политике FULL:

```powershell
python tools/testing/run-gametests.py FULL --offline
python tools/testing/run-gametests.py FULL --legacy --offline
```

Это примеры двух сред, не требование всегда выполнять обе. FAST/STAGE требуют явного `--tests` с точными `Class` / `Class#method`, через запятую, без wildcard. FULL запрещает фильтр. `--plan` проверяет граф и selection: **NOT RUN**, а не GameTest PASS.

`forge-addon/gradle/testing.gradle` собирает каталог из source roots; compatTest включается только с legacy. Все исходники GameTests остаются входами компилятора при смене профиля/selection. `SelectedGameTests` выбирает методы через `RegisterGameTestsEvent`; не обходи selection через source exclusions, GameTestHolder/Generator или `-x`. Сохраняй namespace `tacticalnpcai`, сценарии, assertions, templates, batches, timeouts и test-only clock.

Launcher включает `compileCompatJava`, а `compileJava` уже входит в зависимости GameTestServer. Отдельный предварительный compile не нужен при том же покрывающем launcher invocation; самостоятельная compile-проверка допустима, когда это выбранный минимальный объём. Из `forge-addon`:

```powershell
.\gradlew.bat compileJava compileCompatJava --offline --console=plain
```

Launcher сохраняет уникальные raw `.log`, JSON receipts и изолированный runtime в `forge-addon/build/test-runs/`. Старые миры/config и логи не удаляются автоматически. PASS отдельного GameTest invocation требует exit 0, ровно одного отчёта selection и завершения, ненулевого count и равенства selected = completed = required passed. `NO-SOURCE`, skipped, dry-run, ноль и неполное выполнение не являются PASS. Если появятся optional tests, парсер нужно явно расширить, а не засчитывать их автоматически. Повторное использование receipts не меняет эти требования.

Fixtures должны обеспечивать chunk/entity ticking всей structure в пределах своих bounds и освобождать свои test-only tickets. Memory/LOS assertions выполняются до уничтожающего цель teardown. Факт native выстрела подтверждается actual projectile с учётом отмены EntityJoin; fake GunFireEvent и trigger request его не доказывают. Эти требования к сценариям не меняются ради сокращения запусков.

Core suites определены в `ai-core/run-tests.sh`: FAST может выбирать релевантные suites, неизвестные/повторные имена — ошибка; javac остаётся полной свежей компиляцией во временном каталоге. Исторический `tools/review/run-alpha-probe.sh` не включается автоматически в каждую задачу.

Сохраняй raw logs/CSV/JFR, исходные FAIL и manifests. Сообщай точные версии, команду, selection/среду, actual counts/status, identity артефакта и нерешённые риски. Чтение старого отчёта не является новым выполнением. Для before/after используй сопоставимый замороженный baseline; оригинальный NPCs и AI репозитория — разные эксперименты. Меньшее число выстрелов/активных NPC не является доказательством ускорения; FakePlayer не заменяет human playtest.

## Передача production JAR

При передаче изменённого JAR нужен актуальный production build без combatTests/profile/clientSmoke/legacy flags и source filters, затем verifier именно передаваемых артефактов. Уже применимый результат на тех же входах и SHA можно использовать повторно. Для правок только инструкций, без передачи нового JAR, сборка не нужна.

Из `forge-addon`:

```powershell
.\gradlew.bat build --offline --console=plain
```

Из корня:

```powershell
python -B tools/verify-production-artifacts.py
```

`UP-TO-DATE` допустим при актуальных inputs/outputs, но не является новым запуском тестов. Не добавляй `clean`, `--rerun-tasks` или `-x` без установленной причины; после test flags необходимая production compilation должна удалить test classes из передаваемого JAR. При подозрении на повреждённые outputs сначала установи причину.

Отдельное предложение по инфраструктуре: исследовать безусловный `--rerun-tasks` в GameTest launcher и возможность безопасного Gradle reuse при изолированных outputs. Это отдельная задача с проверкой актуальности артефактов; данное изменение политики launcher, тестовые сценарии и парсер не меняет.
