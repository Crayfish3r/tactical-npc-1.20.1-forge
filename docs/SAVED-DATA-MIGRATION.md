# SavedData и скрытые имена — 2026-10-24

Minecraft 1.20.1 / Forge 47.4.20 / Java 17 / TaCZ 1.1.8-hotfix2.
Реестры принадлежат overworld. Все runtime-изменения выполняются на server thread.

## Имена: `tacticalnpc_names`, schema 1 → 2

Schema2 добавляет nullable `ownerMatchId` к записи имени. Отсутствие поля означает
постоянную административную идентичность либо недоказанное происхождение старой
записи. Такие имена сохраняются после смерти/discard по прежней семантике.
Match API помечает запись временной только после подтверждённого native admission.
KILLED/DISCARDED удаляет временные `entries`, `owners` и weak loaded handle;
UNLOADED_TO_CHUNK/CHANGED_DIMENSION сохраняет имя и принадлежность. Поздно завершившееся
native удаление очищает stale weak loaded handle при запросе counts/list; lookup
уже отвергает removed instance. Временный handle также удаляется при cleanup матча. Удаление матча
освобождает также имена выгруженных участников по известным UUID групп.
Повторная очистка ничего не меняет и не вызывает лишний `setDirty()`.

Schema1 читается без потери имени/UUID/dimension/order. При startup UUID из валидных
старых групп `tacticalnpc_matches` доказывают временное происхождение соответствующих
имён и позволяют их удалить. Имена без такого доказательства сохраняются: исторические
orphan/dead записи schema1 автоматически очистить безопасно невозможно. Это касается
и старых незавершённых миграций/несогласованных резервных копий двух файлов.
Schema2 дополнительно позволяет удалить явно временную запись, если запись её матча
уже была сохранена как удалённая. Файлы регионов не сканируются.

`nextCandidate` schema1 читается совместимо, но старый максимум не используется:
поиск свободного имени возобновляется с базового пула. Занятые имена, включая
выгруженные административные NPC, повторно не назначаются. Сортировка списка
выполняется только по запросу и кешируется до изменения записей; save не сортирует.

## Матчи: `tacticalnpc_matches`, schema 1 → 2

`deactivate` отзывает callback и бой немедленно; до `remove` остаются группы для
очистки, диагностируемые как pendingCleanup. `remove` удаляет доступные загруженные
сущности, освобождает временные имена всех известных участников, удаляет собственные
пустые scoreboard teams и полностью удаляет запись матча. Чужая/пересозданная team
или явно присоединённый посторонний участник сохраняется. UUID погибших участников
удаляются из активных групп при окончательном removal; unload их сохраняет.

Ни policy, ни loaded handles не сериализуются. После restart все сохранённые матчи
закрыты и очищаются. Неизвестный/закрытый match либо неправильная group/member binding
всегда отклоняются на admission, даже после удаления истории. Поздно загруженный NPC
удаляется без боя. Старые поля `ownerMatchId`/`groupId` никогда не обнуляются для
превращения NPC в административного. Новая запись schema7 дополнительно содержит
`matchOwned=true`: потеря обоих полей при наличии marker также закрывает admission, даже если его
значение false или тип повреждён.
Явное временное владение в индексе имён даёт дополнительное доказательство.
Если из старого NBT и обоих реестров удалены абсолютно все доказательства владения,
отличить его от прежнего административного NPC невозможно; патч не угадывает происхождение.

Контракт одноразового произвольного UUID требует памяти об использованных ID.
Schema2 заменяет неограниченные UUID tombstones фиксированным Bloom-фильтром:
1 048 576 бит (128 KiB), семь хешей, неизменный алгоритм в `UsedMatchIds`.
Биты никогда не сбрасываются и не имеют TTL. Ложных отрицаний нет: ранее использованный
ID не откроется. Ложноположительный ответ отвергает новый ID; это консервативный отказ,
а не разрешение старому NPC стрелять. При 100 000 случайных ID приблизительная
вероятность такого отказа около 0,65%; это оценка формулы Bloom, не измерение нагрузки.
При насыщении доступность новых регистраций снижается вплоть до отказа всех ID.
TT должен обрабатывать исключение, использовать новый случайный UUID с ограниченным
числом попыток и сообщать оператору о невозможности регистрации. Автоматического
обнуления/ротации нет. Нельзя удалять фильтр для продолжения в прежнем мире.
Смена алгоритма/размера требует новой схемы и безопасной стратегии миграции.

Все ID schema1, включая пустые завершённые матчи, добавляются в фильтр до очистки.
Размер несжатого пустого schema2 NBT постоянен; размер gzip-файла по мере заполнения
битов может увеличиваться до ограниченного размера фильтра. Это не claim уменьшения
MSPT/GC: измеряются размеры/конечное состояние, а не combat performance.

## Повреждённые данные

Неизвестная schema, неверные типы списков, дубли identity/member/group/match и
повреждённый/отсутствующий used-ID filter вызывают ошибку с именем реестра и schema.
SHA-256 фильтра проверяется при загрузке. Minecraft `DimensionDataStorage` сам
перехватывает decode/IO exceptions; `StrictSavedData` запрещает создать замену,
если `.dat` уже существует или невозможно доказать его отсутствие. Startup прерывается,
пустой реестр не записывается. Для IO-повреждения schema может быть нечитаемой;
диагностика прямо говорит об этом и ссылается на исходную ошибку в логе.
Восстанавливать нужно согласованную резервную копию реестров, scoreboard и entities.
Как и у vanilla SavedData, физическое удаление файла оператором неотличимо от нового
мира; патч не защищает от намеренного удаления всех данных/отката несогласованных backups.

## Имена и диагностика

CustomName сохраняется, CustomNameVisible=false применяется и к legacy NBT.
Существующий Dist.CLIENT renderer `TacticalNpcEntity` запрещает как shouldShowName,
так и конечный renderNameTag (включая Forge event ALLOW). Это не требует команды
на каждого NPC, не меняет alliances/friendly fire и не загружает client classes
на dedicated server. Собственная native team каждой API-группы дополнительно имеет NEVER.
Если администратор вручную присоединит игрока к такой team, на него распространяется
её обычное vanilla NEVER; API игроков в эти teams не перемещает.

`/npc debug diagnostics` выводит names `[permanent, temporary, loaded]` и matches
`[active, pendingCleanup, loaded, matches, members, policies]`. Подсчёт вызывается
только по запросу, не обходит историю каждый tick и не загружает чанки.
