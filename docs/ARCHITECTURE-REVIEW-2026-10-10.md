# Ревью архитектуры и боевого MVP — 10 октября 2026

## Вывод

Проект — работоспособный прототип серверного стрелкового контроллера, пригодный для следующего этапа разработки. Это пока не тактический NPC для публичного сервера: укрытия, память наблюдений, осмысленное наступление/оборона, оружейные профили и массовая нагрузка не реализованы или не проверены.

Целевое направление: собственная сущность NPC, зависимость от TaCZ для оружия, независимое Java-ядро тактики. Текущий адаптер NPCs 2.1.0 полезен как переходная реализация и база сравнения. Новые модели и анимации отложить; для подключения клиента к собственной сущности понадобится минимальное отображение средствами Minecraft.

## Сильные стороны

1. Чистое Java-ядро действительно не импортирует Minecraft, Forge, TaCZ или NPCs. Snapshot и решение immutable.
2. Выстрел, перезарядка и затвор идут через оригинальный TaCZ API. Самостоятельного создания пуль в аддоне нет.
3. Мутации выполняются в серверном цикле; на границах есть проверка server thread. Асинхронных работников пока нет, поэтому их преждевременное введение не требуется.
4. Адаптер снимает исходные goal/target selectors, обнуляет vanilla target и восстанавливает управление. Это предотвращает известные конфликты с исходным дальним и встроенным ближним боем.
5. Задержка реакции, ограниченный поворот и плавная ошибка прицеливания уже отделяют сложность от мгновенного точного наведения.
6. Точные зависимости и исследованные сигнатуры документированы. Своих Mixins нет; Access Transformer затрагивает только проверенные поля vanilla Mob.

## Найденные проблемы

### R1 / P2 — оружие не обслуживается при отсутствии видимой цели

`ai-core/.../CombatBrain.java:19–28`: отсутствие/потеря цели обрабатывается раньше пустого магазина и затвора. `TacticalCombatGoal.java:62–66` удаляет target при потере LoS; `102–105` передаёт `targetKnown=false`. Результат — PATROL вместо RELOAD. При известной, но скрытой цели ядро выбирает SEARCH до проверки магазина.

Сценарий: опустошить магазин, игроку уйти за стену. Новая перезарядка не начинается до повторного обнаружения. Уже начатую перезарядку этот вывод не касается: её продолжает обслуживать upstream TaCZ/NPCs.

Исправление: разделить обслуживание оружия и тактическое намерение. Разрешать reload/bolt без видимой цели, выбирать безопасную позицию отдельно. Добавить проверки «пустой магазин без цели» и «потеря LoS после последнего выстрела».

### R2 / P2 — управление движением не исполняет решение ядра

`forge-addon/.../TacticalCombatGoal.java:105–123`: после `CombatBrain.decide()` движение определяется только `visible`, дистанцией и случайным направлением. Каждый тик вызывается `navigation.stop()`. В `ActionArbiter` поступает только оружейная часть; он возвращает `WeaponAction`.

Даже если ядро начнёт возвращать TAKE_COVER, RETREAT или FLANK, этот исполнитель продолжит стрейф при видимой цели. Простого добавления сенсора укрытий будет недостаточно; навигационный путь также будет отменяться каждый тик.

Исправление: независимые `MovementCommand`, `AimCommand`, `WeaponCommand`; единый результат арбитража с TTL и проверкой владельца. Navigation.stop выполнять при смене/отмене команды, а не как постоянную политику. Сохранить одного владельца движения.

### R3 / P2 — коридор огня не покрывает нативный разброс и продолжение полёта

`TacticalCombatGoal.java:98–100` и `VisibilitySensor.java:46–54`: проверяются два отрезка длиной до цели, с фиксированным расширением AABB. Оригинальный TaCZ затем применяет собственный разброс; в `ModernKineticGunItem.doBulletSpread` также предусмотрен gunpack script `calcSpread`.

Сценарий: союзник находится рядом с направлением выстрела на дальней дистанции, вне фиксированного запаса 0.6 блока; центральный луч проходит, часть дроби/пуль может попасть в союзника. За самой целью живые сущности вообще не проверяются. Для оружия с пробитием это дополнительный риск. Код не подтверждает обещание полного отсутствия friendly fire для произвольного магазинного оружия.

Исправление: определить поддерживаемые свойства выстрела, проверять консервативную область разброса и продолжение траектории для пробивающих боеприпасов. Неизвестные скриптовые свойства ограничивать до отдельной валидации. Если требуется строгий запрет союзного урона, проверить серверный damage-event guard отдельно от предотвращения опасных выстрелов; он не заменяет грамотное поведение.

### R4 / P2 — выдача оружия навязывает SEMI независимо от данных оружия

`forge-addon/.../debug/DebugCommands.java:69–71`: команды spawn/equip создают оружие с `FireMode.SEMI`. Допустимость режима и тактическая работа очередями не определяются по `GunData.getFireModeSet()`. Наличие gun ID проверяется, но совместимость режима — нет.

Сценарий: выдать оружие из gunpack, рассчитанное на другой набор режимов. Контроллер не обеспечивает корректный выбор штатного режима. Даже для автоматов текущая команда не выражает предполагаемую манеру огня.

Исправление: выбирать допустимый режим по метаданным, хранить его в GunSnapshot, отдельно задавать тактическую длину очереди и паузу. Подтвердить результат на настоящих semi/auto/burst образцах; автоматический результат ShootResult.SUCCESS сам по себе этого не доказывает.

## Архитектурные разрывы между документацией и реализацией

Это ограничения текущего MVP, а не утверждение, что перечисленные функции уже были реализованы неправильно.

| Область | Фактическое состояние | Следующий шаг |
|---|---|---|
| `NpcRuntimeAdapter` | Упоминается в архитектуре, интерфейса нет | Выделить реальный контракт среды исполнения |
| Связь с NPCs | Goal, sensor, gun controller, commands принимают AutoGunOperator | Оставить эти импорты только в совместимом адаптере |
| Память | target UUID сразу удаляется при закрытии LoS | ObservationMemory с timestamp, source, confidence, uncertainty |
| Snapshot | Набор boolean; нет позиций наблюдений, cover candidates, оружейного профиля | Составные immutable records и известные координаты |
| Планировщик | Простая цепочка if; без commitment/hysteresis | Тактическое состояние и минимальное время удержания решения |
| Укрытия/фланг | Runtime передаёт false для cover, incomingFire, flank, pathBlocked | Геометрические сенсоры и ограниченная навигация |
| Наступление | effectiveRange берётся из detectionRange; ADVANCE практически недостижим при текущем отборе целей | Разделить радиус обнаружения и рабочую дистанцию оружия |
| Восприятие | Один луч в торс, поиск 360°, aim начинается сразу | FOV и отдельная задержка регистрации наблюдения |
| Упреждение | AimLead существует отдельно, в Forge не подключён | Только после проверки баллистики и скорости по наблюдениям |
| Безопасность | Стрельба только при видимой живой цели | Отдельный ограниченный режим стрельбы по известной точке |
| Резерв | Upstream NPCs даёт бесконечные перезарядки | Явная серверная политика finite/infinite |
| Масштабирование | Локальные лимиты кандидатов/лучей, общих бюджетов и LOD нет | Счётчики, общий бюджет на уровень, измерения |
| Тесты | 35 Java assertions и один составной Forge GameTest, AK-47 SEMI | Отдельные воспроизводимые сценарии, оружейная матрица, 1v4 и нагрузка |

## Нужен ли `[TACZ] NPCs` в будущем

**Для текущего JAR — да.** `mods.toml:23–28` объявляет обязательную зависимость; production-классы напрямую ссылаются на `mod.cdv.tnpc`. Удаление JAR или флага mandatory без рефакторинга не создаст независимый мод.

Сейчас NPCs предоставляет сущность, регистрацию, шаблоны, фракции, экипировку, сохранение, клиентское представление и свою реализацию/обслуживание оружейного оператора.

**Для собственного аналога — архитектурной необходимости нет.** В закреплённом TaCZ `LivingEntityMixin extends Entity implements IGunOperator`; `IGunOperator.fromLivingEntity(LivingEntity)` выполняет cast к интерфейсу. Его серверное обслуживание включает reload, aim, bolt, cooldown synchronization и heat. Это бинарное основание для эксперимента с собственной сущностью на базе PathfinderMob, а не доказательство уже работающего независимого NPC.

Первый независимый срез должен подтвердить initialization/cache/draw/ammo/reload/bolt/sync у собственной сущности. Нельзя автоматически скопировать `AutoGunOperator.onTickServerSide`: это может повторить обслуживание TaCZ или закрепить чужие внутренние зависимости. Сохранять зависимость от самого TaCZ логично: пользовательская цель — пользоваться его оружием и gunpacks.

Предпочтительная последовательность: стабилизировать MVP → выделить контракты → доказать независимый NPC на одном оружии → перенести тактические функции в общее ядро. Не стоит сначала наращивать большие тактические системы внутри AutoGunOperator, чтобы затем переносить их повторно.

Собственной сущности понадобятся регистрация/attributes, spawn/equipment команды, NBT-схема, фракции, серверная синхронизация и минимальный client renderer. Серверная авторитетность не означает возможность добавить новый EntityType на обычный клиент без соответствующего мода. Полноценные модели, анимации, редактор NPC и интерфейсы на этом этапе не нужны.
